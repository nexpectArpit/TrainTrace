# TrainTrace PRD clarification — 2026-11-17

This addendum records requirements clarified during project review without rewriting the original PRD v5.2 baseline.

1. **Dataset scope:** The core dataset selector supports CIFAR-10 and CIFAR-100, with dataset-specific normalization, class counts, labels, holdout evaluation and inference metadata. Every run stores its dataset identity and split provenance.
2. **Layer-level model control:** For the configurable CustomCNN family, a training run must let the user choose convolution feature-block depth and width, classifier width, and dropout. The selected values must be validated and preserved in run configuration, checkpoints, audits, registry metadata, and inference reconstruction. Preset architecture families may retain fixed internal layouts.
3. **Notebook analysis workflow:** Deliver a Jupyter notebook as a first-class analysis companion to the pipeline, suitable for project explanation and viva review. It must select a real run and display its per-epoch metrics, holdout evaluation, confusion matrix, configuration, and checkpoint metadata/tensor shapes. Metrics need a human-readable artifact that is refreshed after each completed epoch, including interrupted runs. Tracked training remains routed through the durable application queue so notebook results are connected to run provenance.
4. **Readable outputs:** Per-epoch metrics are persisted in SQLite and exported to CSV; evaluation details are exported to JSON. Model `.pt` checkpoints remain binary tensor artifacts and are inspected through PyTorch. The current source does not produce metric `.pkl` files; pre-existing external pickle files are not assumed to have a known schema.
5. **Search and reporting:** Users can find investigations/runs across dataset, architecture, optimizer, depth, status, seed, and accuracy. Exported reports include candidate comparison, configurations, epoch metrics, holdout evaluation, audit results, decisions, and registered versions; a combined CSV provides machine-readable run/epoch data.
6. **Accessibility:** Core workflows expose keyboard-visible focus, semantic status announcements, reduced-motion support, responsive layouts, associated form labels, and screen-reader descriptions for charts/progress.
7. **Acceptance:** The new flow is not considered verified until CIFAR-100 has been trained, reloaded, registered, activated, and used for inference; CIFAR-10 behavior and old default-layout checkpoints remain compatible; the notebook displays metrics for completed, stopped, and failed runs and handles an empty local database; search/reporting exports and accessibility checks pass.

Implementation status and outstanding verification are tracked in [the repair report](../audits/2026-11-17/BUG_UI_ARCHITECTURE_NOTEBOOK_FIX_REPORT.md).
