# TrainTrace backend and MLflow architecture review

**Date:** 2026-11-18  
**Scope:** initial static source review of TrainTrace backend, its PRD, and MLflow source checkout at `../mlflow-upstream-retry`, commit `b6c922375ddd3f5816a1324eaec81d343413b2b1`. This was accurate at review time; implementation has since started. Read [the implementation status](BACKEND_FIX_IMPLEMENTATION_STATUS.md) for current fixes and remaining work.

## Executive assessment

TrainTrace has a valid focused backend for a local, single-user deep-learning workflow. It already has useful foundations: validated run contracts, transactional run-and-job admission, a separate worker process, reproducible train/validation splits with recorded hashes, deterministic algorithm settings, per-epoch persistence, managed artifact paths and hashes, immutable model manifests, and an explicit evidence snapshot for decisions.

The main risks are not that TrainTrace lacks all of MLflow's infrastructure. MLflow is a general tracking platform with an abstract tracking-store contract, distinct SQL and artifact-store implementations, normalized run metadata, paginated search, and Alembic database migrations. TrainTrace intentionally has one local SQLite database and one filesystem artifact store. The problem is that some behaviors in this smaller architecture affect correctness, portability, or future maintenance and need stronger boundaries before the project is treated as reliable beyond its current laptop workflow.

**Highest priority at review time:** protect the final test set from repeated model selection; correct preprocessing/transfer-learning semantics; and make the worker's platform assumptions explicit or portable. The CORS concern recorded below was later found to be incorrect for the standard Vite dev flow: `/api` is proxied same-origin by Vite. See the implementation status for the changes and remaining items.

## Prioritized findings

### P1 — Experimental correctness and runtime reliability

| Finding | Evidence and impact | Recommended design |
|---|---|---|
| **Every candidate is evaluated on the test set, then test metrics are available for comparison and selection.** | `backend/tracking/tracker.py` evaluates `test` as soon as each training run completes and writes the result to `evaluation_json`. The compare API returns it (`backend/api/routers/runs.py`, `detail` and comparison response); decisions snapshot it (`backend/api/routers/experiments.py`, decision evidence). Reusing the nominal holdout to compare many candidates leaks test information into model selection and biases the reported final score. This behavior is also explicitly requested by PRD FR-EVL-01, so the PRD and sound evaluation practice conflict. | Select candidates using validation data. Keep the test set inaccessible to candidate comparison and decision screens; evaluate it once after the selected configuration is frozen. If the current academic workflow must show repeated test values, label them as development-set results and require a new untouched final set for the final claim. Update PRD and UI language together. |
| **ImageNet initialization is paired with CIFAR preprocessing, and ResNet's pretrained stem is discarded.** | `backend/core/dataset.py` resizes to 32×32 and normalizes with CIFAR statistics for all architectures. `backend/core/models.py` loads torchvision ImageNet weights; `ResNet18Wrapper` then replaces `conv1` with a fresh 3×3 layer, discarding the pretrained first convolution. MobileNetV2/EfficientNet retain their layers but receive 32×32 CIFAR-normalized images rather than their expected ImageNet normalization/resolution. Thus “Initialize with ImageNet weights” does not describe a consistent transfer-learning setup, and architecture comparisons are not comparable. | Use model-specific, recorded input transforms. Decide whether to preserve/adapt the pretrained stem or train a CIFAR-specific stem; state that explicitly. Persist weight enum/version and preprocessing in run config and registry manifest. Include architecture-specific initialization policy in comparisons. |
| **The worker uses POSIX-only `fcntl` despite configuration claiming Windows support.** | `backend/worker.py` imports `fcntl` at module load and uses `flock` to enforce a single worker. `/api/v1/system/info` also imports `fcntl` (`backend/api/main.py`). `backend/config.py` documents cross-platform behavior including Windows for device selection, but the worker cannot import on Windows. | Either formally scope the product to macOS/Linux and remove Windows support claims, or put locking behind a platform-neutral lock abstraction and add a Windows implementation. Keep lock ownership and worker liveness separate from the hardware/device abstraction. |
| **CORS concern (retracted for the standard dev flow).** | The review overlooked `frontend/vite.config.js`'s `/api` proxy to FastAPI. The browser talks to the Vite origin even when Vite chooses a fallback port, so this does not cause the claimed CORS failure. Direct browser access to FastAPI from another origin is a separate deployment configuration question. | No CORS change is needed for the standard Vite dev flow. Configure exact origins only if direct cross-origin browser access becomes a supported use case. |
| **Cancellation has a check-then-update race.** | `backend/jobs.py:87-102` reads job status, then sets `cancel_requested=1` with no status condition. If the worker completes between those operations, the API can acknowledge a stop request for a completed job and leave a stale cancellation flag. | Perform a conditional state transition inside one `BEGIN IMMEDIATE` transaction (`UPDATE ... WHERE status IN (...)`); inspect affected row count; update queued training-run state in the same transaction; return the final status. |

### P2 — Recovery, data lifecycle, and scalability

| Finding | Evidence and impact | Recommended design |
|---|---|---|
| **Interrupted jobs are marked failed and cannot resume or retry.** | `backend/worker.py:13-27` marks all `RUNNING` jobs failed on worker startup; `backend/core/trainer.py` saves model/optimizer/scheduler state but exposes no resume path. The job schema has no attempt count, lease/owner, retry policy, or idempotency key. Completed epochs survive, but after process/API interruption the user must start a new run. | Define supported guarantees: either make interruption explicitly terminal and offer a “fork from checkpoint” operation, or add checkpoint resume with saved Python/NumPy/CPU/CUDA RNG and data-loader state, job attempts, leases, and recovery rules. Do not imply a run resumes merely because checkpoints exist. |
| **Schema evolution is an ad-hoc startup routine, not a versioned migration system.** | `backend/db/database.py:30-103` creates tables, inspects columns and adds fields on every startup, then writes `PRAGMA user_version=1`; there are no version-specific migration steps. `executescript()` is used around these changes, making the full schema transition difficult to treat as one rollback-safe unit. Future structural changes risk partially upgraded or ambiguous databases. | Introduce numbered, ordered migrations (Alembic or a small SQLite migration registry), backup policy, migration transaction tests, and upgrade/downgrade/recovery instructions. Keep the current local SQLite option; a SQLAlchemy backend is not required just to get sound migrations. |
| **Routers, SQL access, orchestration, serialization, and report generation are coupled.** | `experiments.py` is 363 lines and mixes CRUD, decision policy, evidence snapshot, report rendering, and SQL. `runs.py` owns SQL-heavy detail hydration, JSON decoding, filtering, download validation, and API endpoints. `tracker.py` coordinates training and direct writes. The database helper is centralized, but there is no repository or application-service boundary. This makes transaction rules, API changes, persistence migrations, and isolated unit tests harder. | Add a small architecture: routers validate/translate HTTP; service functions implement use cases and transactions; repositories own SQL; domain contracts/status transitions are centralized; artifact storage is accessed through one service. Do not reproduce MLflow's entire plugin system for a single-user app. |
| **Run comparison is unpaginated and query-amplified.** | `backend/api/routers/runs.py:142-153` loads all run IDs and calls `detail()` per run; `detail()` separately queries metrics, decisions, artifacts and audits (plus audit members). Filtering occurs in Python after all rows and JSON blobs are loaded. This is an N+1 pattern and response size grows with every run/epoch; it risks violating PRD's <300 ms API target as data grows. No measurement was run here. | Add server-side filters and page tokens/limits; fetch comparison summary columns in batched SQL; lazily fetch full run detail, metrics and artifacts. Set response-size and maximum-page contracts. Benchmark against a stated local data volume. |
| **Artifact handling is filesystem-specific and cleanup/retention is undefined.** | Artifacts are written under local `storage/artifacts` and registry checkpoints under local `storage/registry`; DB rows store absolute paths. Checksums and containment checks are good safeguards, but moving the project/storage directory or changing storage roots can strand records. There is no retention, orphan cleanup, or migration utility for moving storage. | Store relative keys or storage URIs, centralize path resolution, add an integrity/orphan scan and explicit backup/restore procedure. Keep local filesystem as the first adapter; add cloud only if the project scope needs it. |
| **Metrics and provenance are partly packed into JSON columns with no schema version.** | `runs.config_json`, `environment_json`, `dataset_json`, `evaluation_json`, and decision evidence/details are serialized blobs; the API hydrates them with `json.loads`. Config snapshots have no schema-version field, so future readers need inferential compatibility logic. | Add `config_schema_version` and `manifest_schema_version`; validate/upgrade snapshots at read boundaries. Keep relational columns for common query/index fields and JSON for evolving detail. Preserve old payloads rather than rewriting scientific evidence silently. |

### P2 — Measurement and audit validity

| Finding | Evidence and impact | Recommended design |
|---|---|---|
| **The recorded “latency per sample” is a dataset throughput estimate, not serving latency.** | `backend/tracking/evaluator.py:evaluate_candidate` starts a timer around iteration over the entire holdout loader. The timed loop includes data-loader work, tensor transfers and batched inference, and divides total duration by sample count; it performs no warmup. The serving path (`backend/api/routers/inference.py`) preprocesses one image and measures a single model forward pass after load/transform. Registry values therefore cannot be compared directly to actual single-image inference latency. | Rename this metric to throughput-derived evaluation time per sample, with method/batch/device metadata; add a separate inference benchmark with warmups, repeated batches, synchronization and p50/p95, clearly stating preprocessing and cold-start boundaries. Never use the current number as a serving SLO. |
| **Protocol B reports population spread but does not define confidence/selection semantics.** | `backend/tracking/evaluator.py` uses `statistics.pstdev` and reports mean, std, min/max and spread. This is mathematically valid for the requested N=5 descriptive report, and `ddof=0` is recorded. It does not provide confidence intervals or block selection based on uncertainty. | Keep the descriptive report, but explain that five seeds and population SD are not a strong inferential guarantee. Add confidence intervals only if statistically justified and include the chosen convention. Avoid automatic model ranking from a small seed set. |
| **Protocol A is exact-replay only on captured runtime/data/source equality.** | The audit checks complete environment and dataset equality, full epoch metric trajectories and holdout loss/accuracy. That is stringent and good, but does not compare every checkpoint tensor hash or all RNG states; its `accuracy_delta` only compares the two replay accuracies. A pass is still a numerical parity assertion, not proof of bitwise-identical model state. | Name its guarantee precisely. If bitwise replay is required, compare checkpoint hashes/state tensors and capture all RNG/library/runtime state; otherwise label it numeric trajectory repeatability. Keep timing outside the parity claim. |
| **Checkpoint state is richer than current recovery behavior.** | `backend/core/trainer.py:143-159` saves model, optimizer, scheduler, CPU Torch RNG and config. It does not save Python/NumPy/CUDA RNG or sampler state; no load/continue code exists. Checkpointing protects model artifacts but does not currently guarantee exact mid-run continuation. | Either document checkpoints as forensic/final artifacts, or complete and validate a resumable checkpoint contract before exposing a Resume action. |

## PRD gaps confirmed by source

These are feature/spec mismatches, not necessarily defects in the intentionally narrow MVP. The PRD should be updated if these are deferred.

| PRD item | Current backend evidence | Status / decision needed |
|---|---|---|
| **FR-DAT-01: CIFAR-10/100, MNIST, Fashion-MNIST, SVHN** | `backend/domain.py` dataset literal and `backend/core/dataset.py` catalog currently support only `cifar10` and `cifar100`. | Partial. Either add the three datasets with correct splits/transforms/class metadata or revise supported scope. |
| **FR-DAT-02: dataset version, ratios, batch and transforms** | Run snapshot stores dataset name/version string, hashes, counts, split hash, normalization and augmentation; batch size is in run config. The snapshot does not record split ratios as an explicit field or a pinned source release/archive identity. | Mostly present; add explicit split fractions and a verifiable dataset release/archive identity. |
| **FR-EXE-03: queue or reject choice** | Queue is always accepted into the single FIFO worker. No API choice is exposed to reject a request when another job runs. | Partial. Add a queue/reject policy or revise the requirement to FIFO queue only. |
| **FR-TRK-03: optional W&B synchronization** | No W&B integration is present in backend dependencies or tracking flow. | Missing. Implement only if credentials/online sync are still a requirement; otherwise mark deferred because offline local-first tracking is already supported. |
| **FR-ART-02: PDF evaluation and confusion-matrix image** | Evaluation and confusion matrix are stored in JSON, and epoch metrics in CSV. No PDF/image renderer appears in the backend. | Partial. Generate the required reports or update the artifact requirement. |
| **FR-LIN-01: interactive lineage graph** | Registry captures a manifest and exposes lineage JSON; current functionality is record/list-oriented rather than an interactive graph. | Partial. A readable lineage view may satisfy the academic reviewer, but it is not the specified graph. Decide and update acceptance criteria. |
| **FR-SRCH-01: global search by tag** | Search/filtering is fixed to known config fields; there is no first-class tags table/API. Compare filters all runs in memory. | Partial. Add formal tags and global paginated search or revise requirement to the current curated filters. |
| **FR-DEC-03: full quantitative evidence snapshot** | Decision snapshot includes holdout evaluation and completed audits. It omits epoch metrics/config/environment/dataset as direct snapshot fields (those remain reachable through run and registry lineage). | Evidence is referenceable but not self-contained/frozen. Freeze the relevant metric rows and provenance hashes in decision evidence, or explicitly define immutable references as sufficient. |
| **FR-CMP-02: latency comparison** | Comparison can show the current latency estimate, whose measurement is throughput-derived (above). | Present but semantically unreliable as serving latency; fix metric before using it for model selection. |
| **NFR-PERF/WCAG** | PRD specifies API response targets and WCAG AA contrast, but no benchmark or accessibility evidence was gathered in this backend review. | Unverified, not proven failed. Define low-cost performance and accessibility acceptance checks when requested. |

## MLflow comparison: what to adapt and what not to copy

At the inspected commit, MLflow separates tracking API contracts from concrete stores: `mlflow/store/tracking/abstract_store.py` defines the store interface; SQL-backed persistence is in `mlflow/store/tracking/sqlalchemy_store.py`; artifact repositories have their own abstraction; database changes use ordered Alembic migrations documented in `mlflow/store/db_migrations/README.md`. Search methods support limits, ordering and page tokens. The UI and backend communicate through explicit service and REST boundaries.

For TrainTrace, the valuable adaptations are:

1. A clean separation between API/router, domain service, persistence repository, artifact store, and job scheduler.
2. Versioned migrations and stable public run/experiment contracts.
3. Paginated server-side search and summary/detail endpoints.
4. A durable job state machine with conditional transitions, recovery policy, and operator-visible attempt/error state.
5. Pluggable boundaries only where the product needs them (e.g. local artifact storage now, alternative database later).

Do **not** adopt MLflow's full multi-tenant backend, SQLAlchemy dialect matrix, auth, plugin registry, async telemetry and GenAI tracing surfaces unless TrainTrace's scope actually expands. MLflow's architecture is evidence for separation and stable contracts, not a mandate to rebuild MLflow.

## Recommended implementation order

1. Correct test-set policy and transfer-learning preprocessing; fix latency naming/measurement. These affect the validity of reported model results.
2. Fix CORS/dev-origin configuration and POSIX lock portability or explicitly narrow supported OS scope.
3. Make job stop transitions atomic; specify recovery, resume/fork and retry behavior.
4. Add versioned DB and JSON-manifest migrations, with backup/recovery documentation.
5. Split routers and tracking code into services/repositories/storage boundaries; add pagination and summary queries.
6. Resolve the PRD gaps table with product decisions, then implement or formally defer each item.
7. Add targeted tests and performance measurements for migration upgrades, cancellation races, worker restart, dataset leakage boundaries, pretrained preprocessing, protocol parity, and large-run comparison.

**Conclusion:** TrainTrace's local-first backend is a useful prototype foundation, but result validity (test leakage, transfer transforms, latency semantics), portability (POSIX lock and CORS port), and operational lifecycle (ad-hoc schema migration, non-resumable failed jobs) need correction before calling it robust. The architecture should gain a few explicit boundaries and versioned contracts rather than imitate MLflow's full platform scale.
